色彩编码格式

2026-09-06

关联阅读：《MIPI-CSI2 协议》讲的是”像素字节怎么打包、怎么在线上传“；本文换一个维度：这些字节代表什么颜色——从 sensor 的 Bayer 马赛克，到 RGB/YCbCr 的编码与色度抽样，再到内存里常见的格式。

〇、先建立画面：像素的”颜色”是层层加工出来的

一张相机的彩色图，不是 sensor”直接拍出来的彩色”，而是经过多级处理：

几个贯穿全文的要点：

  1. RAW 图像的每个像素只有 1 个通道值（只感 R 或 G 或 B 一种光），根本不是”彩色像素”
  2. 同一种”视觉颜色”，在不同阶段叫不同格式：sensor 端 = Bayer 相位 + 位深；ISP 输出 = RGB/YCbCr + 位深 + 色度抽样；内存里 = V4L2 fourcc
  3. 调试时永远先问自己：现在看的是哪个阶段的格式？——线上（CSI-2 DT）、内存（fourcc）、人眼所见（色彩空间）三套口径不能混

一、CFA 与 Bayer：颜色是怎么被”抽样”的

单色 sensor 只有亮度信息。要出彩色，就在每个像素上贴一片微型滤色片（CFA，Color Filter Array），让该像素只感红、绿、蓝中的一种光。

主流是 Bayer CFA，2×2 为一个周期：

  • 绿占 1/2：人眼对绿色最敏感（也是 SNR 最高的通道）
  • 红、蓝各占 1/4

Bayer 有 4 种相位（决定左上角像素滤什么色），由 sensor 硅片上的实际排列决定：

两个易踩的坑：

  1. 每个像素只有 1 通道 → 全彩必须靠 demosaic 插值，插值质量决定”假彩/拉链”伪影（见第三节）
  2. 相位会随 flip 翻转：镜像/旋转后左上角颜色变了。以 RGGB 为例：

所以驱动里一旦配置了 hflip/vflip，上报给 ISP 的 Bayer 相位必须同步改——这正是 V4L2 media bus code 里 SRGGB10 的 SRGGB 前缀在表达的东西（协议篇 6.3 已提，这里补的是”为什么翻转会改相位”）。

例：IMX219 手册标称 BGGR，但它的 hflip/vflip 寄存器会改变读出起始角，实际输出相位随镜像配置漂移——ISP 侧（RK 平台由 sensor 驱动上报的 bus code 决定）必须跟着变，否则红蓝对调。

二、RAW 的”位深”与”值”：它们还不是颜色

RAW 值 = 该像素对应通道的光强（经过 ADC 量化、模拟增益、黑电平偏移），跟”最终显示的颜色”没有直接的数——需要第三节那条链路才算得出。

驱动/调试侧关心的只有三件事：

项 说明 常见值
位深 ADC 量化位数，决定 DT 与打包 RAW8/10/12/14
黑电平 black level 无光时的输出值（非 0） 10bit 常见 64
读出顺序 行/列读出方向 → Bayer 相位 由 flip 决定
  • 黑电平要减掉：sensor 的”零光”输出通常不是 0（留余量防 ADC 底部噪声），demosaic 前若不做黑电平校正，暗部会发灰、偏色
  • 位深 ≠ 打包方式：位深决定 DT 和 MIPI 打包规则（协议篇第二节），但”值→颜色”的语义在 CSI-2 协议里不存在——协议只搬运字节，不解释颜色

结论：sensor 驱动工程师的职责到 RAW 为止——保证位深对、flip 对、黑电平对、DT 对。**”颜色对不对”不是 sensor 驱动的问题**，是 ISP 配置的问题。

三、从 Bayer 到 RGB：demosaic 与 ISP 的调色链

sensor 送出的 Bayer RAW 要变成人眼能看的图，ISP 至少要干这几件事：

步骤 做什么 出错表现
demosaic 用邻居像素插值，把每个像素补成 R/G/B 三通道 假彩、拉链纹、边缘彩边
白平衡 WB 给 R/B 通道乘增益，让灰卡拍出来 R=G=B 整幅偏蓝/偏橙
CCM 3×3 矩阵，把 sensor 滤色片响应”矫正”到标准色度 颜色发假、饱和过度
gamma 亮度的非线性编码，匹配显示特性 整体发灰或对比怪异

驱动工程师真正该懂的：

  • demosaic 是全彩的关键一步：Bayer 每个像素只有 1 通道，所谓”1600 万像素相机”实际 sensor 上就是 1600 万个单通道感光点，全靠插值合成
  • CCM 是偏色调试第一站：sensor 的滤色片响应不等于标准 RGB，各家 ISP 都带 3×3 CCM 表。如果一张图颜色整体不对（不是”红蓝对调”那种结构性错误），先查 CCM / WB，别去 sensor 侧瞎调模拟增益

四、RGB 与 YCbCr：两种承载同一颜色的编码

RGB 面向显示：显示器就是三个子像素叠光。YCbCr 面向传输与压缩：

  • Y：亮度（luma）
  • Cb、Cr：两个色差信号，Cb ∝ (B−Y)、Cr ∝ (R−Y)
  • G 不单独传——由 Y、Cb、Cr 反解出来

为什么存在 YCbCr：

  1. 人眼对亮度敏感、对色度迟钝 → 色度可以降采样省带宽（第五节）
  2. H.264/H.265 等编码本就围绕亮度+色差工作
  3. 兼容黑白显示的历史需求

4.1 转换系数：BT.601 / BT.709 / BT.2020

RGB↔YCbCr 的矩阵随标准不同，对应不同分辨率时代：

标准 场景 Y（全范围，8bit）
BT.601 SD（576i/480i） 0.299R + 0.587G + 0.114B
BT.709 HD（720p/1080p） 0.2126R + 0.7152G + 0.0722B
BT.2020 UHD（4K/8K） 0.2627R + 0.6780G + 0.0593B

Cb、Cr 类似，只是把 (B−Y)、(R−Y) 按幅度归一化后各加 128（8bit）偏置。同一个颜色，用 601 还是 709 算出来的 YCbCr 数值不同——采集与显示端标准不一致就会出现色偏。

4.2 全范围 vs 有限范围（full / limited range）

这是色彩问题里最高频的翻车点。同一个 YCbCr 值，在不同”摆幅约定”下代表不同颜色：

量化 全范围 full（PC swing） 有限范围 limited（TV/studio swing）
8bit Y 0~255 16~235
8bit Cb/Cr 0~255 16~240
10bit Y 0~1023 64~940
  • limited 留出超白/超黑余量，是广播与 HDMI 电视的默认
  • full 是 PC 显示器、大部分抓帧工具的默认
  • 症状：把 limited 当 full 解 → 黑发灰、对比度低；把 full 当 limited 解 → 黑位被裁、暗部死黑

实战：ISP 输出到编码器前常被要求配置成 limited（编码标准默认）；调试抓帧工具看 full。链路两端约定不一致时，先对 “16（Y）是不是纯黑” 这个值。

五、色度抽样：4:4:4 / 4:2:2 / 4:2:0

颜色”编码”之外还有一层：色度在空间上抽稀。人眼对色度不敏感，于是 Cb/Cr 不必每个像素都带：

带宽差异（8bit，4 个像素为例）：

格式 bit/像素 相对 4:4:4 典型用途
4:4:4 24 100% 高质量采集/显示
4:2:2 16 66.7% 广播、YUV422 sensor 输出
4:2:0 12 50% H.264/H.265 编码、NV12 内存

和 CSI-2 的对应：协议里 YUV 长包就是按这个分的——YUV422-8（对应线上 UYVY/YUYV 形态）是最常见的 sensor 直出；YUV420 极少由 sensor 直接输出，多是 ISP 后端合成后给编码器。

注意：4:2:0 要求宽、高都是偶数（色度块是 2×2），奇数分辨率会踩内存布局问题；色度采样位置（UV 落在像素网格的哪个点）在不同标准还有细微差别，普通调试不用深究，但”UV 错半格”的边缘彩色就是它引起的。

六、内存里的常见格式（V4L2 fourcc 视角）

数据离开 CSI 控制器、落进内存后，用 V4L2 fourcc 描述怎么读。和线上的 DT 是两套口径：

fourcc 说明 内存排列 来源场景
YUYV YUV422 packed Y0 U Y1 V（每 4 字节 2 像素） 老式带 ISP sensor / 采集卡
UYVY YUV422 packed U Y0 V Y1（CbCr 换位） 同上，字节序不同
NV12 YUV420 2-plane plane0 = 整帧 Y；plane1 = 交错 Cb Cr 编码器最主流输入（H.264/H.265）
NV21 YUV420 2-plane plane1 = 交错 Cr Cb Android camera 曾用
SRGGB10 RAW10 unpacked 每像素 2 字节（高 10bit 有效） RK 等平台 CSI 解包后落内存
SRGGB10P RAW10 packed 4 像素 5 字节 抓”线上原始形态”

两个关键区别：

  1. packed vs unpacked：多数 SoC 的 CSI/capture 控制器把 RAW10 解包成 16bit/像素再 DMA 落内存（协议篇 6.4 讲过），所以用户态拿到的通常不是线上的 4B/3px 形态；只有”抓线上原始包”的场景才见 SRGGB10P
  2. Cb/Cr 顺序：NV12 的 UV 平面是 Cb 在前，NV21 是 Cr 在前——顺序搞反，画面就是红蓝互换的经典色偏

七、症状对照：色彩篇

MIPI-CSI2 篇第七节已给了协议层症状，这里只补色彩维度的排查：

症状 首查方向
整幅红蓝互换 Cb/Cr 顺序（NV12↔NV21）、UYVY↔YUYV、Bayer 相位错（flip 没同步）
颜色发假/饱和过头 CCM 未配置或配错
整幅偏橙/偏蓝 白平衡（WB）没做或错
黑不黑、白不白、对比度怪 full vs limited range 两端约定不一致
暗部灰蒙蒙 黑电平没减（RAW 阶段问题）
flip 后出现彩色噪点/棋盘格 Bayer 相位 + 读出顺序没跟着镜像改
边缘彩色、拉链纹 demosaic 质量差（低速/简单插值）
UV 错位导致的彩条 4:2:0 宽高非偶数 / plane stride 对齐错

八、最小记忆锚点

  1. **sensor 阶段只有”1 通道/像素”**：记 Bayer 相位 + 位深 + 黑电平
  2. 颜色还原是 ISP 的活（demosaic→WB→CCM），sensor 驱动不负责”颜色对”
  3. 同一视觉颜色有多种承载：RGB888 / YUYV / NV12——按带宽与下游需求选型
  4. 每次对接前对齐三件事：range（full/limited）、采样（4:x:x）、字节序（Cb/Cr 前后、packed/unpacked）
