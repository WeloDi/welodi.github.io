一、中断

  1. 为什么中断不能睡眠？
  • 进程上下文有明确的 task_struct，可以睡眠、被调度。他包含进程的所有属性：状态、调度信息、内存映射、文件描述符、信号处理、资源统计等。
  • 中断上下文不属于任何任务，没有task_struct，因此不能睡眠、不能用 mutex、不能调用可能睡眠的函数，也不可直接访问用户空间地址，只能用自旋锁并要求尽快返回，慢活交给下半部或线程化处理。
  • 如果中断中使用睡眠，后续没人能把它再调度回来，系统直接死锁。

二、DMA

2.1 怎么保证缓存一致性(CPU与DMA)？

  • 硬件方法 - 总线监听：Cache 控制器监听总线，发现 DMA 访问的地址在自己 Cache 里，则标记cache无效，让cpu直接访问内存
  • 软件方法 - 在 DMA 传输前后，软件手动操作 Cache（dma_map_single/dma_unmap_single）：
    CPU 写数据到 buf, 然后flush cache：把dirty 数据写回内存。
    CPU 读数据时，标记cache无效，让cpu直接访问内存。
  • 使用非缓存内存dma_alloc_coherent（速度慢）：把 DMA 缓冲区映射为非缓存的，CPU 访问直接到内存，不经过 Cache

2.2 DMA缓冲区结构

  • 单缓冲区

    就一块buf, CPU 填数据 → dma_map_single → 启动 DMA → 等待完成 → dma_unmap_single

  • 双缓冲区：两块缓冲区交替使用，一块给 DMA，一块给 CPU
  • 环形缓冲区：内存是一块连续区域，但逻辑上首尾相连 怎么回绕：head = (head + 1) % size
    满空判断：
  1. 浪费一个槽位：head == tail 时为空， head = (head + 1) % size == tail 时为满
  2. 加一个额外计数器count 记录当前元素数量。 缺点：多一个变量，需要维护；多核场景要原子操作

7.1 加速度传感器失灵

问题现象：
这是一个平板设备项目，工厂生产中出现个别设备无法翻转。

调试：
具体现象：

  1. 检查了自动旋转开关正常
  2. 系统也处于平板模式
  3. 手动读取（ectool）G-sensor实时数据也正常
  4. 重启可恢复，放置一段时间偶尔也能恢复

复现手法：
不联网停留在 OOBE 界面，然后长时间 suspend（> 35.8 分钟）

根本原因：

  1. 有一个ChromeOS EC传感器中枢的环形缓冲区驱动cros_ec_sensorhub_ring.c，专门处理 EC 上报的传感器数据。
  2. 而EC的时间戳为 32 位微秒计数，驱动中的 bench_date 会检查时间戳，并把 32 位溢出值还原为 64 位连续时间（和处理器对齐）。
  3. suspend 超过一定时间时，会触发溢出判断的边界条件，这个时间刚好是35.8分钟（≈ 2^31 / 1MHz）
  4. 驱动侧的溢出补偿逻辑存在问题，导致时间戳回退。最终被传感器框架判定为乱序数据，导致 G-sensor 数据被丢弃

解决办法：
chromeos内核团队修复溢出还原逻辑。

7.2 LT9611ex快速拔插黑屏

问题现象
设备冷启动后 HDMI 正常，但是快速拔插 HDMI 线，偶尔（低概率）出现检测不到显示器。
日志里偶尔会打印 “HPD 状态没变化”，但实际线是插着的。但是用 i2c 工具直接去读芯片，hpd状态位明明已经变了，驱动却认为没变。这个问题不是必现，插拔越快（1s）越容易出来。

调试过程
一开始肯定先怀疑硬件，交叉验证线、显示器、板子，都没用。后来就在中断处理中加打印，看下中断触发次数。结果发现：中断其实来了，但中断处理线程有时候直接返回了，说不是 HPD 中断。再去查读中断状态的那段，发现驱动读到的老是旧值。原因是内核的寄存器映射开了缓存，而中断状态寄存器没有被标记成“volatile”，所以驱动读的是缓存，不是芯片实时状态。硬件已经报了中断，驱动却以为没有。

继续往下查，看到中断线程判断是 HPD 之后，会去调度一个工作队列。但是那个调度接口设置了WORK_STRUCT_PENDING_BIT 特性：（防止同一个工作项被重复执行）。快速拔插的时候，拔掉时触发工作队列还没跑完，第二次插入来了，调度就被吞了。导致快速拔插没反应。

根因
第一，中断状态寄存器没被标记为volatile，寄存器映射缓存导致驱动读不到硬件实时值，误判中断源。
第二，工作队列调度用的语义是“不重复排队”，连续快速事件会丢，第二次插拔被忽略。

解决方法
第一，把中断相关的寄存器标成易变、不缓存，保证驱动读的是硬件实时值。
第二，在数据结构中添加一个标志位lt9611ex->hpd_event,用来表示有新事件发生
中断线程里先把中断清掉，再置位这个标志位。然后在工作队列中循环判断这个标志位, 如果在队列执行期间有变化，当前队列也会知道，保证HPD状态永远都是最新。

这个问题难在它不是单一逻辑错误，而是缓存机制、工作队列调度语义两件事交织在一起。表面看是 HDMI 检测不到，实际是驱动状态和硬件状态不同步。排查时不能只盯显示链路，要去看中断、缓存。

7.3 LT9611ex外显分辨率异常

问题现象：
在 LT9611EX 驱动开发调试阶段，设备连接某款 4K 显示器时，概率性出现 HDMI 输出锁定在默认分辨率（1024×768）。（概率大约30-40%），交叉验证发现跟着显示器走。有的显示器没问题，有的显示器就会概率出现。

出问题时 dmesg 里能看到 EDID 读取失败，同时中断日志刷屏。

反复插拔线缆有时能恢复，有时依旧锁定。

调试过程：

  1. 用直接读芯片 ID 寄存器 确认 I2C 通信是正常的。

  2. 出问题时查看中断计数 /proc/interrupts 在短时间内暴涨，CPU 占用也明显升高。说明触发了中断风暴。
    检查设备树中断脚是电平触发（低），然后用示波器抓中断引脚（桥接芯片 INT 输出脚），看到中断信号一直在低电平。

  3. 审查中断处理函数
    打印中断状态寄存器观察值，发现HPD中断状态是被清掉的，但是有其他值存在。然后看芯片手册发现这个值对应的是EDID就绪中断。
    在中断处理函数（下半部）中只清除了hpd中断位。所以会反复触发中断。

  4. 关联 EDID 读取失败
    中断风暴抢占CPU 导致 EDID 读取的等待线程被反复抢占，最终超时失败。
    同时还发现 EDID 就绪中断在某些显示器上到达得比预期晚，而驱动里设置的等待超时偏短，两者叠加导致概率性失败。

问题根因
主因：中断清除不完整，只清了 HPD，没清 EDID ready，导致低电平中断风暴发生。
诱因：EDID 等待超时偏短，部分显示器 EDID ready 到达晚。
中断风暴抢占 CPU，使 EDID 等待线程无法及时调度，形成恶性循环。

7.4 LTE probe不到

问题描述：
在生产过程中，针对 LTE 跑检测项时，出现大量 runtime_probe 检测 Modem 节点失败、报错”Modem 节点不存在”的问题

调试：

  1. runtime_probe 由上层服务调用，用于检测 Modem 节点。log 一直显示 Modem 节点不存在，但写脚本循环检查发现 wwan0 网络接口一直存在，说明底层 Modem 硬件和驱动加载正常
  2. 怀疑 LTE 加载流程较慢，于是增加 runtime_probe 的探测延时，让它晚点 probe。效果好了一些，但问题仍然存在
  3. 通读整个加载流程的log，发现在runtime_probe执行检测前, Hermesh 为初始化 eSIM 会临时抑制 Modem/0 节点。而 runtime_probe 恰好在这个窗口期通过 Shill 检测 Modem 节点，导致找不到节点而超时报错。

解决
Shill 中新增 Cellular.PrimaryMultiplexedInterface 属性，暴露稳定的 wwan0 接口，让 runtime_probe 基于 Shill 提供的接口探测，不再受 ModemManager 节点状态影响。

7.5 MT7925蓝牙问题

问题现象：
系统开机后，蓝牙（MT7925）概率性显示为“关闭”，点击打开无反应。（冷重启恢复）

分析：

  1. 一开始觉得应该是开机初始化问题，然后检查log，发现usb也已经枚举了，fw也加载成功了，但是他报WMT命令被打断：

    就疑惑开机过程中，系统还在启动，用户态服务还没完全起来，信号环境很干净，为什么会有信号打断 WMT 等待？

  2. 然后模拟复现手法，准备脚本压测复现(检查开机后hci0状态是不是up running):
    2台机热重启:三天不复现 （热重启不会触发正常的关机流程，而是走专用流程，所以不会下发shutdown信号）
    2台机冷重启:三天不复现
    2台机关机-开机：三天不复现。
    然后我自己随手拿一台机手动执行关机-开机操作十几次突然复现到了。（没有装固件日志抓取，于是测试了下冷重启恢复）
    但是冷重启能恢复，会不会是蓝牙芯片内部状态问题，那这个状态会不会是在开机前就异常了

  3. 查看代码：
    drivers/bluetooth/btmtk.c

    TASK_INTERRUPTIBLE 表示等待可以被信号打断。
    所以在系统关机时，系统会向所有进程发送 SIGTERM，蓝牙驱动的 WMT 等待被信号打断，驱动直接跳到错误路径，没有等固件完成关闭动作
    这个代码路径在开机时也会走，但只有在关机时信号环境才足够“脏”，才会触发。开机时信号干净

根因：
MT7925 蓝牙模块在关机时没有真正断电（USB 总线仍带电），模块内部状态寄存器可能卡在“半关闭”状态。
下次开机时，驱动重新初始化，发送 WMT 命令，但固件因为上次关机状态没清干净，不再响应，导致初始化失败。
