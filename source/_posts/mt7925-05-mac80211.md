## 文档概述

mac80211 与驱动的接口就是一张 `struct ieee80211_ops`。本文把 MT7925 的这张表按功能拆开讲清楚：哪些回调是 MT7925 自己的、哪些直接复用 mt792x/mt76 的公共实现，以及 **MLO（多链路）如何在 mac80211 的链路模型上与驱动对接**。

---

注意最后一行：**它不是 `static const`，而是 `EXPORT_SYMBOL_GPL`**。原因是 `mt792x_get_mac80211_ops()` 会**复制一份并打补丁**：

```c
ops = mt792x_get_mac80211_ops(&pdev->dev, &mt7925_ops, (void *)id->driver_data, &features);
```

同一个 `mt7925_ops` 被 PCIe/USB、不同 capability 的板子共用，靠这个辅助函数生成"每设备一份"的副本再注册。所以**不要去改全局 `mt7925_ops`**，运行期改的是副本。

## 二、按功能分类

| 分类 | 回调 | 实现来源 |
| --- | --- | --- |
| 生命周期 | `start`、`add_interface`、`config` | MT7925 自己（`mt7925/mac.c`/`main.c`） |
| | `stop`、`remove_interface`、`flush` | mt792x 公共 |
| 数据面 | `tx` | `mt792x_tx`（公共） |
| | `wake_tx_queue`、`release_buffered_frames` | mt76 框架 |
| 管理帧 | `mgd_prepare_tx`、`mgd_complete_tx`、`start_ap`、`stop_ap`、`channel_switch_beacon` | MT7925 自己 |
| STA | `sta_state`（`mt76_sta_state`）、`sta_pre_rcu_remove` | mt76 框架 → 转调 `drv_ops.sta_add/sta_event/sta_remove` |
| | `set_key`、`sta_set_decap_offload`、`ampdu_action`、`sta_statistics` | MT7925 自己 + mt792x |
| 扫描 | `hw_scan`、`cancel_hw_scan`、`sched_scan_start/stop` | MT7925 自己 |
| 信道上下文 | `add/remove/change_chanctx`、`assign/unassign_vif_chanctx` | MT7925 自己 |
| 驻留信道 | `remain_on_channel`、`cancel_remain_on_channel` | MT7925 自己 |
| 统计/ethtool | `get_stats`、`get_et_*`、`get_survey`、`get_txpower` | mt792x/mt76 |
| 时间同步 | `get_tsf`、`set_tsf` | mt792x |
| 省电/休眠 | `suspend`、`resume`、`set_wakeup`、`set_rekey_data` | MT7925 + mt792x |
| MLO | `vif_cfg_changed`、`link_info_changed`、`change_vif_links`、`change_sta_links` | MT7925 自己 |

一眼能看出的结论：**mt792x/mt76 已经把"通用无线设备"的部分做完了**，MT7925 的 `main.c` 主要写三块：接口/管理帧、扫描与驻留、以及 MLO。

## 三、STA 的添加不是在 `sta_state` 里做的

这是读 mac80211 驱动最容易踩的坑：

```c
.sta_state = mt76_sta_state,     /* ❌ 这里看不到芯片代码 */
```

`mt76_sta_state()` 是框架函数，真正的芯片动作通过 `mt76_driver_ops` 转发：

```c
static const struct mt76_driver_ops drv_ops = {
	.sta_add   = mt7925_mac_sta_add,
	.sta_event = mt7925_mac_sta_event,
	.sta_remove = mt7925_mac_sta_remove,
};
```

调用链：

```plaintext
mac80211 (关联完成/删除 STA)
    → ops->sta_state = mt76_sta_state()
         → drv_ops.sta_add / sta_event / sta_remove
              → mt7925_mac_sta_add()
                   ├─ mt76_wcid_alloc()              分一个 wcid（对应 WTBL 表项）
                   ├─ mt792x_vif_to_bss_conf()       拿链路配置
                   ├─ mlink = container_of(wcid, struct mt792x_link_sta, wcid)
                   ├─ mt76_connac_mcu_uni_add_dev()  通知固件"新设备"
                   └─ mt7925_mcu_add_sta()           MCU STA_REC_UPDATE（含 EHT/MLD TLV）
```

`sta_event` 处理的是"STA 状态变化"（authorized / associated 等），`sta_remove` 负责回收 wcid 与 MCU 记录。**MLO 的每个链路各有一个 wcid**，所以这三个回调里到处是 `link_id` 与 `valid_links` 判断。

## 四、`vif_cfg_changed` 与 `link_info_changed` 的分工

mac80211 的 MLO 支持把"VIF 级"和"链路级"的变化拆成两个回调——这是新旧驱动的分水岭（老驱动只有 `bss_info_changed`）：

| 回调 | 承载的变化 | MT7925 的动作 |
| --- | --- | --- |
| `mt7925_vif_cfg_changed` | VIF 级：关联/去关联（`BSS_CHANGED_ASSOC`）、IPv6 NS offload、ARP 过滤、PS 使能（`BSS_CHANGED_PS`）、4addr/beacon 变更等 | 走 `BSS_INFO_UPDATE` 类的 MCU 命令，作用于整个 MLD |
| `mt7925_link_info_changed` | 链路级：`BSS_CHANGED_ERP_SLOT`、`BSS_CHANGED_BASIC_RATES`、`BSS_CHANGED_QOS`、`BSS_CHANGED_BEACON`/`BEACON_ENABLE`、`BSS_CHANGED_MCAST_RATE`、带宽/信道上下文变化（`BSS_CHANGED_*MW`）等 | 需要知道 `link_id` 才能定位具体链路，因此从 `info->link_id` 取 |

写代码时的直接后果：**"改一个链路的东西"绝不能写进 VIF 级回调**，否则 MLO 场景下会把两条链路一起改掉。反过来，PS / ARP 这类"整个 MLD 一份"的配置调 VIF 级即可。

## 五、扫描：`hw_scan` → MCU，结果由事件送回

扫描在 MT7925 上是**固件做的事**，驱动只是搬运参数与结果：

```plaintext
mac80211: ieee80211_scan 请求
   → ops->hw_scan = mt7925_hw_scan()
        ├─ 检查状态（是否已扫描/是否在 ROC/是否 MLD 关联中）
        ├─ mt792x_mutex_acquire()         取 MT76_STATE_MCU_RUNNING 与总线
        ├─ 组装 MCU UNI_CMD(SCAN_REQ) TLV（SSID、信道列表、扫描类型、随机 MAC 等）
        └─ mt7925_mcu_send(...)
               ↓ 等待（或异步）
固件扫描完成
   → RX 事件 MCU_UNI_EVENT_SCAN_DONE
        → mt7925_mcu_scan_event()          解析 TLV，挂到 dev->scan_event_list
             → mt7925_scan_work（workqueue）
                  ├─ 解析每条 TLV：基本信息 / 每信道信息 / NLO（sched scan）
                  ├─ ieee80211_scan_completed() 或 ieee80211_sched_scan_results()
                  └─ 释放 skb
```

`sched_scan`（PNO）走同样的事件通道，只是没有 `scan_completed`，改为每次命中都上报结果：

```c
.sched_scan_start = mt7925_start_sched_scan,
.sched_scan_stop  = mt7925_stop_sched_scan,
```

关键细节：**扫描事件在 MCU 事件分发里是 `return`（skb 不释放）**——因为 skb 会被挂进 `scan_event_list` 交给 work 处理（见第 3 篇的 `mt7925_mcu_uni_rx_unsolicited_event()`）。这是这块代码最容易出泄漏的地方。

## 六、信道上下文与 `chanctx`

MT7925 完整实现了两种信道上下文模型，所以既支持"单信道多接口"，也支持 MLO（多条链路同时占用不同信道）：

```c
.add_chanctx        = mt7925_add_chanctx,
.remove_chanctx     = mt7925_remove_chanctx,
.change_chanctx     = mt7925_change_chanctx,
.assign_vif_chanctx = mt7925_assign_vif_chanctx,
.unassign_vif_chanctx = mt7925_unassign_vif_chanctx,
```

`struct mt792x_chanctx` 里保存 `hw_value` / `mt76_chanctx` 等，`mt792x_assign_vif_chanctx` 之类的公共实现负责把 chanctx 与 vif（链路）绑定。MLO 下 mac80211 会为每条链路分配 chanctx，驱动需要保证 `band_idx` 与信道的对应关系，这也是"MLO 只能 2.4G + 5G 或 5G + 6G 组合"之类限制的实现位置。

### 驻留信道（ROC）

```c
.remain_on_channel        = mt7925_remain_on_channel,
.cancel_remain_on_channel = mt7925_cancel_remain_on_channel,
```

ROC 在 MT7925 上由固件支持（`MCU_UNI_CMD(ROC)` + `MCU_UNI_EVENT_ROC`）：

- `mt7925_remain_on_channel()` 下发 ROC 命令，并启动 `dev->phy.roc_timer`；
- 固件在驻留结束/被抢占时通过 `MCU_UNI_EVENT_ROC` 报告，`mt7925_mcu_uni_roc_event()` → `mt7925_roc_work` 完成收尾；
- **MLO 场景有独立的 ROC 逻辑**（需要同时把多条链路的驻留安排好），代码里能看到 MLD 判断的分支。

这也解释了为什么"关联/认证时射频必须切到目标信道"这件事是必要的：`mgd_prepare_tx` / `mgd_complete_tx` 与 ROC 配合，保证 offchannel 的管理帧能在正确信道上收发。

## 七、MLO 的两个"链路变更"回调

```c
.change_vif_links = mt7925_change_vif_links,   /* vif 增加/删除链路 */
.change_sta_links = mt7925_change_sta_links,   /* sta 增加/删除链路 */
```

语义（mac80211 侧）：

| 回调 | 触发时机 | 驱动要做的事 |
| --- | --- | --- |
| `change_vif_links` | 协商出新的 MLD 链路组合、某条链路被激活/去激活 | 为每条链路分配 `struct mt792x_bss_conf`（`mt792x_vif_to_link()` 懒分配）、维护 `valid_links`、下发 `BSS_INFO_UPDATE` |
| `change_sta_links` | 对端 STA 在 MLD 上增删链路 | 为每个链路分配 `struct mt792x_link_sta`（含 wcid）、更新 WTBL 与 `STA_REC_UPDATE`（MLD TLV） |

配套的"链路 → 数据结构"映射函数是这一层的核心 API：

```c
mlink = mt792x_vif_to_link(mvif, link_id);      /* → struct mt792x_link_sta */
mconf = mt792x_vif_to_bss_conf(vif, link_id);   /* → struct mt792x_bss_conf */
```

**所有链路相关的回调都必须先做这一步转换**，拿不到就直接返回错误。MLO 相关的典型 bug 都是"改了默认链路而不是 `link_id` 指定的那条"。

## 八、小结

1. `mt7925_ops` 是**被复制后使用**的全局表（`EXPORT_SYMBOL_GPL`），改它没用，要看 `mt792x_get_mac80211_ops()` 生成的副本。
2. 一半回调是 mt792x/mt76 的公共实现；MT7925 专属逻辑集中在**接口/管理帧、扫描与 ROC、MLO** 三块。
3. **STA 的芯片动作不在 `sta_state` 里**，它在 `mt76_sta_state()` → `drv_ops.sta_add/sta_event/sta_remove` → `mt7925_mac_sta_*`。
4. MLO 拆成两级回调（`vif_cfg_changed` / `link_info_changed`）与两个链路变更回调（`change_vif_links` / `change_sta_links`），驱动侧一律用 `link_id` 索引 `mt792x_bss_conf` / `mt792x_link_sta`。
5. 扫描/ROC 的结果都来自 MCU 事件，事件 skb 的所有权在 `mt7925_mcu_uni_rx_unsolicited_event()` 里决定——这是排查内存问题的高发区。
