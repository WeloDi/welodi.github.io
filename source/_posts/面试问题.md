## 一、中断

1. 为什么中断不能睡眠？
- 进程上下文有明确的 task_struct，可以睡眠、被调度。他包含进程的所有属性：状态、调度信息、内存映射、文件描述符、信号处理、资源统计等。
- 中断上下文不属于任何任务，**没有task_struct**，因此不能睡眠、不能用 mutex、不能调用可能睡眠的函数，睡眠会导致死锁。**只能用自旋锁**并要求尽快返回，慢活交给下半部或线程化处理。
- 如果中断中使用睡眠，后续没人能把它再调度回来，系统直接死锁。

1. 中断的完整流程：[中断流程](/2026/06/12/Interview/#中断流程)
```c
外设拉中断
  → GIC 路由到目标cpu
  → CPU 切 IRQ 模式，保存硬件现场：PC → LR_irq、CPSR → SPSR_irq，跳向量表
  → 汇编入口保存现场：把 R0–R12、LR、SPSR 压入 IRQ 栈
  → 通用中断处理函数do_IRQ 查 irq_desc找到对应的中断处理函数handler
  → 写 EOI 通知 GIC 中断处理完毕
  → 弹栈恢复现场 SPSR→CPSR、LR→PC、R0–R12
  → 检查 pending 软中断/tasklet，执行 do_softirq
  → 返回源程序
```

1. 中断下半部：见 [中断下半部机制](https://welodi.github.io/2026/08/05/linux%E9%9D%A2%E8%AF%95%E9%A2%98(%E5%9F%BA%E7%A1%80)/#6-%E4%B8%AD%E6%96%AD%E4%B8%8B%E5%8D%8A%E9%83%A8%E7%9A%84%E5%87%A0%E7%A7%8D%E6%9C%BA%E5%88%B6%E7%9A%84%E5%8C%BA%E5%88%AB%E4%B8%8E%E9%80%82%E7%94%A8%E5%9C%BA%E6%99%AF)

关键权衡：
- 延迟：线程化中断有专属线程，通常延迟更可预测。但调度器繁忙时可能延迟变大。
- 资源：工作队列共享 worker 池，比每个中断一个线程更省资源。但如果多个 work 共享一个 worker，一个睡眠可能拖累同队列其他 work。

需要“专属、高优先级、确定延迟”走线程化中断；需要“共享、省资源、灵活排队”走工作队列。

## 二、并发与竞争
**怎么避免竞争？**
> 只要多个线程可能同时访问“同一把锁保护的共享可变状态”，就无法从调度层面绝对保证锁不竞争，只能通过设计消除共享、消除锁、串行化或分片来做到“没有竞争”或“几乎不竞争”。

**怎么避免死锁？**
死锁四个条件：
- 互斥：资源一次只能一个线程持有。 -- 所有线程按同一个顺序获取锁。
- 占有且等待：持有锁的同时等待其他锁。--要么一次拿到全部锁，要么一个都不拿。
或者先拿一个全局大锁，再操作内部资源，但会降低并发
- 不可剥夺：锁不能强行抢走。 -- 使用 tryLock(timeout)，拿不到就释放已持有的锁，退避后重试。
- 循环等待：线程之间形成环状等待。 -- 不可变对象、无锁结构、消息队列、单线程处理。
这是最根本但往往最难完全做到。

破坏任意一个即可避免死锁。

### RCU
全拼Read-Copy-Update，他是一种同步机制，主要用于读多写少的并发场景。

**机制：**
读者直接读，不加锁。写者要修改时，复制一份副本，修改副本，然后把指针切换到新副本。等所有读操作都退出后，再释放原来的内存。

**代价**
写的成本高：要复制、替换、等待读操作退出
内存延迟释放：旧数据不能马上 free
多个写者之间通常还要额外互斥：RCU 主要保证读侧无锁，不保证写者之间无锁。
读者可能读到旧数据：RCU 不保证你立刻看到最新值。


## 三、[DMA](https://welodi.github.io/2026/09/13/mt7925-02-pcie-bus/#4-1-DMA%E7%BB%93%E6%9E%84%E4%BD%93-%E5%88%9D%E5%A7%8B%E5%8C%96%E9%93%BE%E8%B7%AF)

3.1 怎么保证缓存一致性(CPU与DMA)？
- **硬件方法** - 总线监听：Cache 控制器监听总线，发现 DMA 访问的地址在自己 Cache 里，则标记cache无效，让cpu直接访问内存
- **软件方法** - 在 DMA 传输前后，软件手动操作 Cache（dma_map_single/dma_unmap_single）：
                         CPU 写数据到 buf, 然后flush cache：把dirty 数据写回内存。
                         CPU 读数据时，标记cache无效，让cpu直接访问内存。
- **使用非缓存内存**dma_alloc_coherent（速度慢）：把 DMA 缓冲区映射为非缓存的，CPU 访问直接到内存，不经过 Cache

3.2 DMA缓冲区结构
- 单缓冲区
 > 就一块buf, CPU 填数据 → dma_map_single → 启动 DMA → 等待完成 → dma_unmap_single
- 双缓冲区：两块缓冲区交替使用，一块给 DMA，一块给 CPU
 ```

 +-----------+     +-----------+
| Buffer A  |     | Buffer B  |
+-----------+     +-----------+
     ↑                  ↑
   DMA 用             CPU 用
   （下一轮互换）
 ```
- 环形缓冲区：内存是一块连续区域，但逻辑上首尾相连
```
    +-------------------------------+
    |  slot0 | slot1 | slot2 | ...  |
    +-------------------------------+
             ↑               ↑
            tail            head
           (消费者)        (生产者)

生产者往 head 写，写完 head 前移
消费者从 tail 读，读完 tail 前移
```
怎么回绕：head = (head + 1) % size 
满空判断：
1. 浪费一个槽位：head == tail 时为空， head = (head + 1) % size == tail 时为满
2. 加一个额外计数器count 记录当前元素数量。 缺点：多一个变量，需要维护；多核场景要原子操作

## 七、ROS2
ROS2 是一个分布式计算框架

### 7.1 ROS2核心概念 
1. **节点**（Node）: 节点是ROS2中最小的计算单元，类似于一个独立的进程。一个节点通常负责一项专门功能

2. **话题**（Topic）: 话题是节点间的**异步**通信通道，采用**发布-订阅**（Pub-Sub）模式
特点：
- 发布者和订阅者解耦，互不知道对方存在
- 支持一对多、多对一的通信关系
- 适合传感器数据、状态广播、控制指令
```sh
发布者A ──┐
          ├──> [ 话题 /topic ] ──> 订阅者A
发布者B ──┘                    └─> 订阅者B
```

3. **服务**（Service）: 服务是节点间的**同步**通信机制，采用**请求-响应**（Request-Response）模式
特点：
- 客户端发送请求，等待服务器响应（阻塞式）
- 一对一的同步通信
- 适合需要立即反馈的操作（如设置参数、查询状态）
```sh
客户端节点                       服务端节点
    |                               |
    | ---- Request 请求 ----------> |
    |                               | 
    |                          执行服务回调
    |                               |
    | <--- Response 响应 ---------- |
    |                               |
```

4. **消息**（Message）: 消息是节点间通信的数据载体。
5. **动作**（Action）: 动作用于需要长时间执行的任务，提供目标、反馈和结果。

### 7.2 DDS
DDS的全称是Data  Distribution Service，也就是数据分发服务。他采用以数据为中心的发布-订阅模型：DCPS
基本结构是Domain，他的作用是控制通信范围：只有同一个 Domain 内的节点才能互相通信

质量服务策略QoS （Quality of Service）：是 DDS 中用于约束发布-订阅通信行为的一组策略。
通信建立的前提是：Topic 名一致、消息类型一致、QoS 兼容


## 八、RTOS
**定义**
RTOS：能在**确定的时间**内完成指定任务、并对外部事件做出响应的操作系统。
实时不等于“快”，而是**确定性**（时延可预测、有上界），即最坏情况下的响应时间可以分析出来。

**rtos特性**
- 抢占式调度：高优先级任务一旦就绪，立刻抢占 CPU
- 多任务：任务（task/thread）是最小调度单位，每个任务有独立栈和优先级
- 确定性：调度延迟、中断延迟、上下文切换时间有上界，最坏执行时间(WCET)可分析
- 任务间同步与通信：信号量、互斥量、事件标志组、消息队列、邮箱
- 中断管理：ISR 要短，慢活交给任务处理（和 Linux 中断下半部的思想一致）
- 高精度定时器：系统 tick、软件定时器、超时机制
- 资源管理：互斥量支持优先级继承/天花板，解决优先级反转
- 体量小、可裁剪：内核几 KB ~ 几十 KB，可跑在无 MMU 的 MCU 上

**rtos和linux区别**
> 标准 Linux 的不可抢占区（关中断、关抢占、自旋锁、中断处理程序等）比较多、而且有些可能比较长，导致最坏调度延迟大且不确定，所以实时性可能不好；RTOS 的不可抢占区通常很少、很短，并且有明确上限，所以高优先级任务能在有界时间内抢占，实时性好

- 实时性：RTOS 是硬实时；主线 Linux 是软实时，需 PREEMPT_RT 补丁才接近硬实时
- 调度策略：RTOS 按固定优先级抢占（同级可时间片轮转）；Linux 默认 CFS，追求吞吐与公平，不保证单个任务的延迟上界
- 内存管理：RTOS 多无 MMU、无虚拟内存，所有任务共享同一地址空间；Linux 必须有 MMU，进程独立地址空间，内核态/用户态隔离
- 内核结构：RTOS 是高度可裁剪的小内核，通常和应用编成一个固件；Linux 是宏内核 + 可动态加载模块，支持多进程
- 抢占粒度：RTOS 内核基本全程可抢占，关中断时间很短；Linux 存在不可抢占区（自旋锁、关中断临界区）
- 体量与生态：RTOS 为 KB 级，协议栈/文件系统常常外挂；Linux 为 MB 级，网络、文件系统、多用户等生态完整
- 典型场景：RTOS 用于单一用途、资源受限、确定性要求高的场合（电机、穿戴、Sensor Hub）；Linux 用于复杂多功能（网关、HMI、摄像头）
- 补充：二者也常组合使用，例如异构多核 A 核跑 Linux + M 核跑 RTOS，各有分工

### 8.1 **freeRTOS通信机制**
FreeRTOS 给任务间同步与数据交换提供的机制，按"从重到轻"排列：

- **队列 Queue**：最核心也最常用的机制。FIFO 传数据，任务与任务、任务与中断都能用，支持阻塞超时
  发送的是数据本身（按值拷贝），传大块数据时传指针以避免拷贝开销

- **信号量 Semaphore**：不传数据，只传"事件/资源可用"这个信号
  - 二值信号量：用于同步（如 ISR 通知任务"数据来了"），**不能当互斥量用**，因为它没有优先级继承
  - 计数信号量：管理多个同类资源（缓冲区槽位、连接池），也可做事件计数

- **互斥量 Mutex**：保护共享资源，**带优先级继承**，是解决优先级反转的默认手段
  递归互斥量允许同一任务多次获取（自嵌套）

- **事件标志组 Event Group**：一个 bit 表示一个事件，可以同时等待多个事件（按位与/按位或），也能一次通知多个任务，适合"多条件组合触发"

- **任务通知**：最轻量，每个任务自带一个 32 位通知值，不需要创建任何内核对象，速度和 RAM 开销都优于信号量和队列
  可替代二值信号量、计数信号量、事件组；但只能"一对一"（发给指定任务），也不缓存数据

- **流缓冲区 / 消息缓冲区**：面向"数据流"场景
  - Stream Buffer：连续字节流，适合串口、DMA、音频等
  - Message Buffer：带长度前缀的离散报文，一次读写一条完整消息

### 8.2 **什么是优先级反转？**

举例：低优先级任务持有锁 → 中优先级任务抢占 CPU → 高优先级任务在等这把锁，却被那个中优先级任务压着，导致“高优先级反而最后才执行”。
```sh
高优先级 H ───── 等锁（被阻塞）
中优先级 M ───────── 运行（不依赖这把锁，纯抢占）
低优先级 L ── 持锁 ── 被抢占，锁释放不掉
=> H 的等待时间取决于 M 的运行时长，优先级关系被“反转”
```
危害：破坏实时性，且多个中优先级任务时等待时间无界。

解决办法：
1. **优先级继承**：
当高优先级 阻塞在 低优先级 持有的锁上时，L 临时继承 H 的优先级, 释放后，L 恢复原来的低优先级。FreeRTOS 的 mutex 默认支持，Linux rt_mutex 也支持
1. **优先级天花板**：
给每把锁预先设定一个“天花板优先级”，任何持有者立刻提升到该优先级，也能顺带避免死锁。但对优先级规划要求高
1. **避免共享资源**：
用无锁结构（无锁队列/无锁环形缓冲区/无锁链表/RCU）代替互斥。
1. **缩短临界区**
锁持有时间越短，反转影响越小

## 十、通信协议

### [i2c](https://welodi.github.io/2026/06/12/Interview/#IIC)
- 半双工 串行 同步总线 
- 上拉电阻作用：iic总线开漏输出，无法输出高电平

**i2c不通排查步骤：**
先确认 I2C 能不能访问到它
```sh
i2cdetect -y -r <bus> # 扫总线，检查设备地址是否存在
```
分三种情况：
1. **完全扫不到新设备地址：**
- 先确认器件上电情况：量 VCC、上拉电阻是否焊接、上电时序与延时是否满足手册要求
- 确认设备树中的地址 与 手册地址是否一致，是否地址冲突
- 物理层：示波器/逻辑分析仪看 SCL/SDA 有没有波形；速率过高或走线太长

2. **能扫到地址，但驱动 probe 失败**
- 先手动读寄存器（比如CHIP ID），确认链路本身没问题，把问题缩小到驱动侧
```sh
i2ctransfer -y 1 w1@0x10 0x00 r1   # 在 bus 1、地址 0x10 上读 0x00 寄存器
```
- 常见原因：
  - `compatible` 与驱动的 of_device_id 不匹配。
  - probe 里访问寄存器失败：供电/时钟还没开就去读写
  - 资源申请失败：gpio / regulator / clock / irq 拿不到；返回 `-EPROBE_DEFER` 属正常，表示依赖资源还没就绪，内核稍后会重新 probe
  - 上电时序不满足：复位释放后需要的延时没加够

3. **能扫到，也能 probe，但“无功能”或者读写超时**
- 寄存器没真正写进去：需要解锁/写使能、时序不对、或被别处覆盖 —— 用 `i2ctransfer` 回读确认
- 中断不工作：dts 里 interrupt-parent / 触发类型（边沿 vs 电平）配错，或没清中断状态导致只触发一次
- 电源管理：设备被 runtime PM 下电了，访问前没上电；或 suspend/resume 后寄存器没恢复
  
- 看总线是否被“死锁”？测量 SDA 和 SCL 的对地电压，如果某条线一直低，就是死锁了
- 核对i2c频率是否与手册匹配
- 上拉电阻不合适：上拉电阻太大导致上升沿太慢，高速下波形还没到高电平就被采样了，导致超时。

**主机没收到ACK的原因？**
本质是：第 9 个时钟周期，从机没有把 SDA 拉低
原因：
- 地址不对：设备树配错？硬件接错？
- 从机没工作：VDD、GND 没接好，RESET 一直拉低
- 上拉/电平问题：没上拉/上拉太弱，上升沿太慢，上拉电压和从机 VDD 不匹配
- 时序/信号问题：速率太高、线太长、总线电容大
- 总线死锁：SDA 被某个设备一直拉低

  └──→ 循环

### CANopen
- CAN 是一种多主方式的串行通讯总线, 但是CANopen通信中有1个主节点，其他全都是从节点。
- 采用差分信号传输，只需要 CAN_H 和 CAN_L 两根线

核心：**对象字典**（Object Dictionary）
每个 CANopen 设备内部都有一个对象字典，存储着设备的所有参数、数据和配置。

**报文 ID**
```c
报文 ID = 功能码（4位） + 从机地址（7位）
```

**通信方式**：
- PDO(过程数据对象):速度快，周期性，无需应答，用于实时数据，长度<= 8字节，高优先级

- SDO(服务数据对象)：速度慢，按需，需应答，用于参数配置，长度任意，低优先级

**流程**：
```c
┌─────────────────────────────────────────────────────┐
│                    主站                             │
│                                                     │
│  NMT：管理网络状态                                   │
│  SDO：配置参数（读/写对象字典）                       │
│  PDO：收发实时数据                                   │
│  SYNC：周期同步信号                                  │
└─────────────────────────────────────────────────────┘

                        │ CAN 总线

┌─────────────────────────────────────────────────────┐
│                    从站                             │
│                                                     │
│  对象字典：所有参数和数据                             │
│  PDO：实时数据（位置、速度、IO）                      │
│  SDO：配置参数                                       │
│  EMCY：故障上报                                      │
└─────────────────────────────────────────────────────┘
```

### usb
- 主从架构：主机轮询，设备不能主动发起传输，所有事务由主机发起
- 差分信号 D+/D-，上拉电阻决定速度：全速/高速上拉 D+，低速上拉 D-

**设备状态**
```c
Attached → Powered → Default → Address → Configured → Suspended
```

**连接过程（枚举）**
```c
1. 设备插入，Hub 检测到 D+/D- 电平变化，通过自己的中断端点上报"端口状态变化"
2. 主机查询 Hub 端口状态，确认有设备接入，等待约 100ms 去抖（debounce）
3. 主机使能端口并发出总线复位（SE0 ≥ 10ms）
   复位后设备进入 Default 状态：默认地址 0，只使用端点 0 的控制管道
4. 主机用地址 0 读设备描述符
   先只读前 8 字节，取出 bMaxPacketSize0（端点0 最大包长）
   再读完整设备描述符：VID/PID、设备类、配置数量等
5. SET_ADDRESS：主机分配唯一地址（1~127），设备进入 Address 状态
6. 用新地址读配置描述符（连同接口描述符、端点描述符一起返回）
7. 主机按 设备类 / VID-PID / 接口类 匹配驱动（usb_device_id 表）
8. SET_CONFIGURATION：选定一个配置，设备进入 Configured 状态，端点使能
9. 驱动绑定到接口（usb_driver.probe），创建设备节点，开始数据传输
```

**描述符层级**
```c
设备描述符（1 个）
  └──配置描述符（≥1 个）
        └──接口描述符（≥1 个，一个接口对应一个功能/驱动）
              └──端点描述符（≥0 个）
```

**四种传输类型**
- 控制传输：枚举与配置，走端点 0，可靠
- 批量传输：大数据量、无实时要求（U 盘、网卡）
- 中断传输：周期性小数据（键盘鼠标、HID）
- 等时传输：实时音视频，保证带宽但不重传

### 11.1 [imx219 驱动](/2026/08/08/imx219-driver/)
> [mipi-csi2](https://welodi.github.io/2026/09/04/MIPI-CSI2/)
> [色彩编码格式](https://welodi.github.io/2026/09/06/color-encoding/#4-2-YUV-%E7%9A%84%E5%88%86%E9%87%8F%E4%B8%8E%E5%90%8D%E8%AF%8D)


**usb camera与mipi camera区别**
操作系统自带 UVC 类通用驱动，摄像头通过标准描述符告诉主机“我是摄像头、支持哪些分辨率、格式、控制项”
MIPI 摄像头没有等价的 UVC 标准，MIPI CSI-2 只在“传输层”规定怎么把图像数据从摄像头传到 SoC，需要针对传感器和平台做适配。

**V4L2:**
V4L2 框架通过 v4l2_device、v4l2_subdev、video_device 三个核心对象，把复杂的摄像头硬件（Sensor、ISP、CSI 等）抽象成统一的软件模型，并配合 Media Controller 管理数据流水线，最终通过 /dev/videoX 等设备节点暴露给用户空间。
```sh
V4L2 框架
  │
  ├──→ v4l2_device：设备实例容器
  ├──→ v4l2_subdev：子设备（Sensor/VCM/ISP）
  ├──→ video_device：字符设备节点（/dev/videoX）
  ├──→ Media Controller：拓扑管理（Entity/Pad/Link）
  └──→ 用户空间接口：/dev/videoX、/dev/v4l-subdevX、/dev/mediaX
```

> v4L2是用户空间采集视频的标准接口，负责怎么取帧。媒体管线用来描述一个复杂的媒体硬件拓扑。
> 每个硬件模块在 Media Controller 中是一个 entity，每个 entity 有输入/输出 pad，pad 之间通过 link 连接。一整条从 source pad 到 sink pad 的路径，就是一条 pipeline。


**数据流向：**
```sh
Sensor 驱动              CSI 驱动      ISP 驱动          V4L2 capture 驱动
  |                         |            |        _____________|_____________________
  ▼                         ▼            ▼        ▼            ▼                    ▼
Sensor ──MIPI CSI-2──> CSI Receiver ──> ISP ──>  DMA ──> 内存/V4L2 Buffer ──> V4L2 video node（/dev/videoX） ──> 用户空间
  │                       │              │        │            │                      │                             │
RAW Bayer             RAW Bayer    RAW→RGB/YUV  RGB/YUV     RGB/YUV                  出队                      取帧/处理/还帧
RGGB/BGGR/            透传         去马赛克/3A   搬运        (或RAW)                                            循环采集
GRBG/GBRG                          色彩校正/缩放
```
**应用获取数据方式：**
内存映射 (MMAP) ：用户请求内核分配缓冲区，并映射到用户空间。应用直接读取映射后的内存，零拷贝，效率最高。适用连续视频流采集
直接读取 (Read) ：应用像读文件一样，通过 read() 系统调用从驱动拷贝数据。适用静态图片采集

速率关系：
```sh
# 像素速率与帧率的关系
Pixel_rate = 每帧总像素数 × fps  = (H total)×( V total ) × fps

# 像素速率与 MIPI 速率的关系
MIPI 传输的是比特，而像素速率是像素，中间要乘上每像素比特数（bpp），bpp根据传输格式变化

Lane_rate ≥ （HTS × VTS × fps × bbp）/ Lan数   #如果是双边沿采样还要再除以2
                 |
                 ▼ 
Lane_rate ≥  Pixel_rate × bpp / lan数
```

**probe流程：**
```c

```

**启停流：**
s_stream(1) -> imx219_start_streaming:
```
1. pm_runtime 上电
2. 写入当前模式的整张寄存器表
3. 应用所有 V4L2 control 当前值
4. 写 MODE_SELECT=0x01 启动 streaming
5. 锁定 hflip/vflip（streaming 期间禁止切换,会破坏 Bayer 顺序）
```

s_stream(0) -> imx219_stop_streaming:
```c
1. 写 MODE_SELECT=0x00 进入 standby
2. 解锁 hflip/vflip
3. pm_runtime 下电
```

排查：
1. i2ctransfer 手动读 CHIP ID正常，读写Streaming寄存器回读正确
2. 读Clock Lane Status寄存器：发现不是LP11状态
3. 查看数据手册上电时序，发现是链路层问题
根因：
IMX219 的[D-PHY](https://welodi.github.io/2026/09/04/MIPI-CSI2/#%E5%9B%9B%E3%80%81D-PHY-%E4%BF%A1%E5%8F%B7%E4%B8%8E-HS-%E6%97%B6%E5%BA%8F) 在 standby 模式下不会自动进入 LP-11，必须先进 streaming 再退回 standby 让 D-PHY 状态机初始化一次。host 的 clock lane 检测超时，所以 CSI 永远收不到同步

### 12.1 加速度传感器失灵
**问题现象**：
这是一个平板设备项目，工厂生产中出现个别设备无法翻转。

**调试**：
具体现象：
1. 检查了自动旋转开关正常
2. 系统也处于平板模式
3. 手动读取（ectool）G-sensor实时数据也正常
4. 重启可恢复，放置一段时间偶尔也能恢复

复现手法：
不联网停留在 OOBE 界面，然后长时间 suspend（> 35.8 分钟）


**根本原因**：
1. 有一个ChromeOS EC传感器中枢的环形缓冲区驱动cros_ec_sensorhub_ring.c，专门处理 EC 上报的传感器数据。
2. 而EC的时间戳为 32 位微秒计数，驱动中的 bench_date 会检查时间戳，并把 32 位溢出值还原为 64 位连续时间（和处理器对齐）。
3. suspend 超过一定时间时，会触发溢出判断的边界条件，这个时间刚好是35.8分钟（≈ 2^31 / 1MHz）
4. 驱动侧的溢出补偿逻辑存在问题，导致时间戳回退。最终被传感器框架判定为乱序数据，导致 G-sensor 数据被丢弃


**解决办法**：
chromeos内核团队修复溢出还原逻辑。


### 12.2 LT9611ex快速拔插黑屏
**问题现象**
设备冷启动后 HDMI 正常，但是快速拔插 HDMI 线，偶尔（低概率）出现检测不到显示器。
日志里偶尔会打印 “HPD 状态没变化”，但实际线是插着的。但是用 i2c 工具直接去读芯片，hpd状态位明明已经变了，驱动却认为没变。这个问题不是必现，插拔越快（1s）越容易出来。

**调试过程**
一开始肯定先怀疑硬件，交叉验证线、显示器、板子，都没用。后来就在中断处理中加打印，看下中断触发次数。结果发现：中断其实来了，但中断处理线程有时候直接返回了，说不是 HPD 中断。再去查读中断状态的那段，发现驱动读到的老是旧值。原因是内核的寄存器映射开了缓存，而中断状态寄存器没有被标记成“volatile”，所以驱动读的是缓存，不是芯片实时状态。硬件已经报了中断，驱动却以为没有。但是加了这个以后，问题并没有消失，于是继续往下查：

中断线程判断是 HPD 之后，会去调度一个工作队列。但是那个调度接口设置了`WORK_STRUCT_PENDING_BIT` 特性：（防止同一个工作项被重复执行）。快速拔插的时候，拔掉时触发工作队列还没跑完，第二次插入来了，调度就被吞了。导致快速拔插没反应。

**根因**
第一，中断状态寄存器没被标记为volatile，寄存器映射缓存导致驱动读不到硬件实时值，误判中断源。
第二，工作队列调度用的语义是“不重复排队”，连续快速事件会丢，第二次插拔被忽略。

**解决方法**
第一，把中断相关的寄存器标成易变、不缓存，保证驱动读的是硬件实时值。
第二，在数据结构中添加一个标志位lt9611ex->hpd_event,用来表示有新事件发生
中断线程里先把中断清掉，再置位这个标志位。然后在工作队列中循环判断这个标志位, 如果在队列执行期间有变化，当前队列也会知道，保证HPD状态永远都是最新。
```c
while (atomic_xchg(&lt9611c->hpd_event, 0)) {
  读hpd
  和驱动记录的状态对比，只有变了才处理
}
```
 
这个问题难在它不是单一逻辑错误，而是缓存机制、工作队列调度语义两件事交织在一起。表面看是 HDMI 检测不到，实际是驱动状态和硬件状态不同步。排查时不能只盯显示链路，要去看中断、缓存。


### 12.3 LT9611ex外显分辨率异常

**问题现象：**
在 LT9611EX 驱动开发调试阶段，设备连接某款 4K 显示器时，概率性出现 HDMI 输出锁定在默认分辨率（1024×768）。（概率大约30-40%），交叉验证发现跟着显示器走。有的显示器没问题，有的显示器就会概率出现。

出问题时 dmesg 里能看到 EDID 读取失败，同时中断日志刷屏。

反复插拔线缆有时能恢复，有时依旧锁定。

**调试过程：**
1. 用直接读芯片 ID 寄存器 确认 I2C 通信是正常的。

2. 出问题时查看中断计数 /proc/interrupts 在短时间内暴涨，CPU 占用也明显升高。说明触发了中断风暴。
检查设备树中断脚是电平触发（低），然后用示波器抓中断引脚（桥接芯片 INT 输出脚），看到中断信号一直在低电平。

3. 审查中断处理函数
打印中断状态寄存器观察值，发现HPD中断状态是被清掉的，但是有其他值存在。然后看芯片手册发现这个值对应的是EDID就绪中断。
在中断处理函数（下半部）中只清除了hpd中断位。所以会反复触发中断。

4. 关联 EDID 读取失败
中断风暴抢占CPU 导致 EDID 读取的等待线程被反复抢占，最终超时失败。
同时还发现 EDID 就绪中断在某些显示器上到达得比预期晚，而驱动里设置的等待超时偏短，两者叠加导致概率性失败。


**问题根因**
主因：中断清除不完整，只清了 HPD，没清 EDID ready，导致低电平中断风暴发生。
诱因：EDID 等待超时偏短，部分显示器 EDID ready 到达晚。
中断风暴抢占 CPU，使 EDID 等待线程无法及时调度，形成恶性循环。



### 12.4 LTE probe不到

**问题描述**：
在生产过程中，针对 LTE 跑检测项时，出现大量 runtime_probe 检测 Modem 节点失败、报错"Modem 节点不存在"的问题

**调试**：
1. runtime_probe 由上层服务调用，用于检测 Modem 节点。log 一直显示 Modem 节点不存在，但写脚本循环检查发现 wwan0 网络接口一直存在，说明底层 Modem 硬件和驱动加载正常
2. 怀疑 LTE 加载流程较慢，于是增加 runtime_probe 的探测延时，让它晚点 probe。效果好了一些，但问题仍然存在
3. 通读整个加载流程的log，发现在runtime_probe执行检测前, Hermesh 为初始化 eSIM 会临时抑制 Modem/0 节点。而 runtime_probe 恰好在这个窗口期通过 Shill 检测 Modem 节点，导致找不到节点而超时报错。

**解决**
 Shill 中新增 Cellular.PrimaryMultiplexedInterface 属性，暴露稳定的 wwan0 接口，让 runtime_probe 基于 Shill 提供的接口探测，不再受 ModemManager 节点状态影响。


### 12.5 MT7925蓝牙问题

**问题现象：**
系统开机后，蓝牙（MT7925）概率性显示为“关闭”，点击打开无反应。（冷重启恢复）

**分析：**
1. 一开始觉得应该是开机初始化问题，然后检查log，发现usb也已经枚举了，fw也加载成功了，但是他报WMT命令被打断：
```sh
Bluetooth: btusb_mtk_hci_wmt_sync: Wait for WMT event timeout
Bluetooth: hci0: Failed to send wmt cmd (-110)
Bluetooth: hci0: Failed to set up the WMT
Bluetooth: hci0: Execution of wmt command interrupted  //说明 WMT 被打断了
```
就疑惑开机过程中，系统还在启动，用户态服务还没完全起来，信号环境很干净，为什么会有信号打断 WMT 等待？

2. 然后模拟复现手法，准备脚本压测复现(检查开机后hci0状态是不是up running):
2台机热重启:三天不复现         （热重启不会触发正常的关机流程，而是走专用流程，所以不会下发shutdown信号）
2台机冷重启:三天不复现
2台机关机-开机：三天不复现。
然后我自己随手拿一台机手动执行关机-开机操作十几次突然复现到了。（没有装固件日志抓取，于是测试了下冷重启恢复）
但是冷重启能恢复，会不会是蓝牙芯片内部状态问题，那这个状态会不会是在开机前就异常了

3. 查看代码：
drivers/bluetooth/btmtk.c
```c
err = wait_on_bit_timeout(&data->flags, BTMTK_TX_WAIT_VND_EVT,
				  TASK_INTERRUPTIBLE, HCI_INIT_TIMEOUT);
	if (err == -EINTR) {
		bt_dev_err(hdev, "Execution of wmt command interrupted ");
		clear_bit(BTMTK_TX_WAIT_VND_EVT, &data->flags);
		goto err_free_wc;
	}

err = wait_on_bit_timeout(&data->flags, BTMTK_TX_WAIT_VND_EVT,
				  TASK_UNINTERRUPTIBLE, HCI_INIT_TIMEOUT);
```
TASK_INTERRUPTIBLE 表示等待可以被信号打断。
所以在系统关机时，系统会向所有进程发送 SIGTERM，蓝牙驱动的 WMT 等待被信号打断，驱动直接跳到错误路径，没有等固件完成关闭动作
这个代码路径在开机时也会走，但只有在关机时信号环境才足够“脏”，才会触发。开机时信号干净

**根因：**
MT7925 蓝牙模块在关机时没有真正断电（USB 总线仍带电），模块内部状态寄存器可能卡在“半关闭”状态。
下次开机时，驱动重新初始化，发送 WMT 命令，但固件因为上次关机状态没清干净，不再响应，导致初始化失败。


## 十三、常见问题
### 13.1 怎么排查栈溢出？什么情况下会导致栈溢出？
常见导致栈溢出的情况:
- 递归过深或无限递归 / 调用链太深
- 局部变量太大
- 线程栈太小

排查：
Linux 下先看 dmesg / coredumpctl，再用 GDB 看调用栈（命令：bt/bt full）和 栈指针寄存器（命令：info registers rsp），最后用 ASan、-fstack-protector-all、-Wframe-larger-than 定位具体代码。

| 现象 | 结论 |
| --- | --- |
| GDB 大量重复调用帧 | 递归过深/无限递归 |
| 栈指针 rsp 接近 [stack] 低地址 | 调用栈耗尽 |
| `*** stack smashing detected ***` | 栈缓冲区溢出 |
| ASan 报 stack-overflow | 调用栈耗尽 |
| ASan 报 stack-buffer-overflow | 栈缓冲区越界写 |
| 只有某线程崩溃 | 线程栈太小或线程内大局部变量 |

### 13.2 C语言字节对齐的规则，为什么要字节对齐？
规则：按照所有成员变量的“对齐要求”中的最大值对齐。
CPU和内存之间通常按“字节”或总线宽度访问，比如 32 位总线一次读 4 字节。如果 int 放在地址 0x1001，未对齐，CPU 需要读两次再拼接，某些架构甚至直接触发异常。
对齐访问通常一次内存操作完成；未对齐访问可能跨缓存行、跨页，需要多次访问，速度明显下降。

### 13.3 为什么要分用户空间和内核空间？用户态怎么切到内核态？
本质是 CPU 特权级 + 虚拟内存权限 + 操作系统设计 共同决定的。核心目的就一个：
让不可信的应用程序和可信的内核隔离开，防止程序破坏系统、访问硬件、篡改其他进程。

内核空间:
```sh
0xFFFFFFFF  ┌─────────────────────┐
            │ 固定映射区 (fixmap)  │  如 0xFFF00000 - 0xFFFFFFFF
            ├─────────────────────┤
            | 持久映射区           |  将高端内存（物理地址高于896MB的部分）中的页面长期映射到内核空间
            ├─────────────────────┤
            │ vmalloc 区          │ ~ 120 MB,虚拟地址连续物理地址不连续，每次都要操作页表。ioremap映射到这里的专用区
            ├─────────────────────┤
            │ 隔离区 (Gap)         │  8 MB，作为“哨兵”，用于检测从一个区域到另一个区域的越界访问
            ├─────────────────────┤
            │ kmalloc区           │  地段内存，约 896 MB，讲物理地址线性映射到这里，基于 slab 分配器，有缓存，速度快
0xC0000000  └─────────────────────┘
```

用户空间通过：系统调用、异常（如缺页）、外设中断切到内核态
