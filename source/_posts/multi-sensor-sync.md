## 一、时间同步的作用与挑战

> 多传感器融合（VIO/SLAM/ADAS）的前提，是每个样本都携带"在哪个时刻采集"的准确时间戳：只有把各传感器的采样对齐到**同一时间基**，才能把 IMU 数据内插到相机的曝光中点、把点云与图像按同一物理时刻配对。

**时间同步要解决的三类问题：**

1. **硬件时钟漂移**：不同设备的晶振频率存在微小差异（普通晶振 ±20~50ppm），且频率随温度漂移；误差随时间线性累积——20ppm 的时钟一天约漂移 1.7s。软件"对表"只能校正相位（offset），校正不了频率（skew），因此需要持续驯服而非一次同步。

2. **网络延迟波动**：基于网络/总线传输的传感器（以太网摄像头、USB 设备）受交换机排队、队列调度、驱动缓冲影响，包到达时刻 ≠ 真实采样时刻，时间戳不确定性增强。

3. **缺乏统一时基**：多数嵌入式传感器（IMU、Camera、麦克风）未接入 GPS/PTP 等高精度授时系统，各自本地时钟自由漂移，且漂移方向与速率各不相同。


## 二、时间同步常用方案

**按精度与物理基础分层，实际系统通常组合使用：**

| 方案 | 精度 | 依赖 | 特点 |
| ---- | ---- | ---- | ---- |
| NTP（网络时间协议） | ms 级 | 需联网 | 部署简单；受路由/排队抖动影响，断网即失效 |
| PTP/gPTP（IEEE 1588 / 802.1AS） | µs 级 | 局域网 | 硬件时间戳打点、主从分发，适合车载以太网/TSN |
| GPS/北斗授时 + PPS | ns 级 | 需卫星信号+天线 | 原子钟级绝对时间基准 + 秒脉冲硬触发 |
| PPS + NTP/chrony | µs 级 | 混合 | 用 PPS 驯服本地时钟，兼顾绝对时间与成本 |

1. **NTP**：经 UDP 从服务器取时间。优点是无额外硬件；缺点是精度受网络延迟/抖动限制在 ms 级（120km/h 下 10ms 车已走 33cm），且依赖外部网络——汽车进隧道、机器人进地库断网即失准，不符合功能安全。

2. **PTP/gPTP**：局域网内主时钟（Grandmaster）向从设备分发时间，借助网卡硬件时间戳，精度达 µs 级。gPTP（802.1AS）专为车载/工业场景优化，是 TSN 的时间基。局限：只能覆盖网络可达节点，且"分发的只是时间数值"，无法提供物理触发沿。

3. **GPS/北斗 + PPS**：卫星本身携带原子钟（ns 级），接收机既输出时间数据，又在每个整秒边沿输出一根物理电平跳变（PPS）。PPS 可直接接传感器触发引脚，实现硬件级"同时按下快门"，是精度最高的绝对基准。局限：天线只能接主控，室内/隧道不可用。

4. **组合落地**：GPS（绝对原子时 + 硬触发脉冲）→ 主控（PPS 驯服本地晶振，chrony/pps-gpio）→ PTP/gPTP 广播给各子设备。GPS 是源头，网络是管道——缺了 PPS 硬线就没有物理触发，缺了 PTP 时间则无法分发到每一路传感器。

### 2.1 行业落地：机器人（单主控为主）

> 前文 GPS→PTP 金字塔是**自动驾驶/车路系统**的典型形态；机器人行业大多用不到最顶层的 GPS，方案取决于传感器分布与是否有实时控制域。

**室内单机机器人（主流形态）**

- Camera、IMU、ToF 等全部挂在**同一颗主控 SoC**（RK3588/Jetson）上，时间戳由内核 V4L2/IIO 驱动统一打点、天然同源（同一 `CLOCK_MONOTONIC`）——**不存在跨设备时钟漂移，自然不需要 PTP/GPS**；
- 实际要做的是：相机曝光中点时间戳（rolling shutter 补偿）、IMU 中断/硬件 FIFO 时间戳、数据侧近似对齐（ROS `message_filters::ApproximateTime` 按时间戳窗口配对，或紧耦合 VIO 直接插值）。

**分布式 / 多机 / 室外场景**

- 设备各自独立才需要跨设备同步：以太网 PTP/gPTP（µs 级，配合网卡硬件时间戳）；ROS2 对应 `/clock` 机制（ROS1 单机单时钟，无分布式同步）；
- 室外带 GPS 场景（巡检、物流园区）：主控用 PPS 驯服本地晶振后经 PTP 分发；
- 激光雷达选型经验：机械雷达（如 Velodyne）走 PTP；固态雷达（如 Livox）自带 PPS/GPRMC 接口，直接 PPS 驯服内部时钟（同时校准旋转相位）。

**人形机器人：跨时钟域对齐**

人形机器人天然是**多计算域**系统——感知（Linux 视觉 SoC）与全身控制（FPGA/实时 MCU，常走 EtherCAT/私有总线）是两个独立时钟域，还要在 1kHz 控制环内融合关节/IMU 反馈，同步问题比轮式机器人多一个维度：

1. **感知域（视觉-IMU 状态估计）**：同 SoC 时间戳 + 曝光中点补偿；高要求团队再加硬件对齐——相机 FSIN/曝光信号与 IMU（支持同步输入的型号）DRDY/采样窗口对齐，由 FPGA/PLL 统一分发采样触发，让 IMU 样本真正落在曝光中点附近。
2. **控制域（关节/力觉/躯干 IMU）**：编码器、六维力传感器经 EtherCAT 由 **Distributed Clock（DC）** 在 µs~ns 级拉齐整条总线的伺服/传感器时钟，采样统一到 1kHz 控制 tick。
3. **跨域（感知 ↔ 控制）**：室内无人形机器人**没有 GPS**，常见两种做法：
   - 一方输出**本地 PPS/同步 tick**（如 Linux GPIO 产生 1kHz/1PPS 给 FPGA/MCU，或反向由控制侧驱动 Linux 中断打时间戳）；
   - **共享帧计数 + 时间戳映射**：控制侧每 tick 广播帧号，感知侧记录"帧号 ↔ 内核时间"映射表，在线换算到同一时间基。
   - PTP 是次选：实时控制域常为 EtherCAT/FPGA，并不都支持 PTP。

> 小结：机器人行业靠"单主控 + 内核统一时间戳 + 软件对齐"解决大部分同步问题；只有跨设备（多机/以太网雷达）才上 PTP，只有室外 GPS 场景才上 PPS。人形机器人的独特难点不是协议选型，而是**两个异构实时域之间的时间对齐**。

### 2.2 行业落地：汽车（自动驾驶）

汽车正好是第二章"GPS 是源头、PTP 是管道"金字塔的**标准形态**——时间同步已从定制方案变成车载以太网的标准配置：

1. **GNSS/PPS 提供绝对基准**：车辆常年室外运行，智驾域控普遍带 GNSS（RTK），以 PPS 驯服本地时钟，提供绝对原子时与整秒硬触发；
2. **gPTP 域内分发**：多域控（智驾/座舱/车身）与各传感器接入节点之间走车载以太网 **IEEE 802.1AS gPTP**（AVB/TSN 时间基），µs 级；AUTOSAR 通过时钟同步模块（StbM）对接 gPTP，向各应用提供统一时间；
3. **相机经 GMSL/FPD-Link 串行链路接域控**：像素与曝光由域控侧 ISP 统一控制，时间戳在域控打点（仍需要曝光中点补偿）；多相机再靠 FSIN 菊花链做硬件帧同步（属采样同步范畴）；
4. **功能安全要求时钟监测**：ISO 26262 下 GNSS/gPTP 失步或时钟故障必须可检测并降级（如 GNSS 丢失时切换自由运行 + 告警），这是汽车行业除"NTP 精度不足"外选择硬件授时的另一原因。

> 对比小结：汽车有成熟车载以太网 + 全域 GNSS → GPS 源头 + PTP 管道是标准架构；机器人（尤其室内）单主控为主、无 GNSS，靠统一时间戳 + 软件对齐；人形机器人则多一层异构实时域的跨域对齐。
